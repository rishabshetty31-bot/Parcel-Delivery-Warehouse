# Parcel Delivery Performance Warehouse — SQL Server design

**Status:** Step 4 design with Steps 5–7 implemented and SQL-tested through guarded local Gold publication. **Governing rules:** [PROJECT_SPEC.md](PROJECT_SPEC.md), [SOURCE_CONTRACTS.md](SOURCE_CONTRACTS.md), [EVENT_AND_CUTOFF_RULES.md](EVENT_AND_CUTOFF_RULES.md), and [DATA_GENERATION_PLAN.md](DATA_GENERATION_PLAN.md). The public edition's [validation summary](VALIDATION.md) records the later end-to-end replay. This design does not change the approved business rules.

**Step 7 implementation clarification (2026-10-01):** The five reporting views select from run-parameterized inline functions. Candidate validation calls those same functions before publication, so the candidate projection cannot silently differ from the published view. `ctl.publication_attempt` is one additional technical audit table, retaining successful, rejected, and rolled-back publication attempts. An exclusive transaction-owned application lock serializes pointer switches. `ctl.refresh_run.status='PUBLISHED'` means the run has been published at least once; only `ctl.published_run` identifies the currently active run. Gold's approved `decimal(19,6)` hour columns round each row to six decimals; exact duration reconciliation uses Silver integer seconds. See [validation summary](VALIDATION.md).

**Step 5 implementation note (2026-09-28):** At Step 5, only `ctl` and `bronze` had been created and exercised. The implemented control model adds `BRONZE_COMPLETE` as a success status before Silver processing and `ctl.source_file.loaded_row_count int NOT NULL DEFAULT 0` for parsed-to-loaded reconciliation. Each Bronze row adds `source_name varchar(32) COLLATE Latin1_General_100_BIN2 NOT NULL`, constrained to its table's source and included in the `(source_file_id,run_id,source_name)` foreign key. This closes the cross-source provenance gap in the proposed two-column FK. Raw `nvarchar(max)` fields use `Latin1_General_100_BIN2`; future raw equality must still compare `CONVERT(varbinary(max), value)` and `DATALENGTH(value)` because ordinary SQL string equality can ignore trailing spaces. The implementation and checks are documented in `VALIDATION.md`.

**Step 6A implementation note (2026-09-28):** The implemented Silver subset is `silver.row_resolution`, `silver.customer`, `silver.customer_location`, `silver.customer_primary_location`, `silver.depot`, and `silver.service_level`. The row-resolution table allows all six source names for the future Step 6B, but only the four reference sources currently receive rows. `ctl.reference_stage` records the latest run-scoped reference-stage state, and `ctl.reference_stage_attempt` preserves each attempt's failure or success across retries; both are technical audit tables, not business sources. A completed stage rejects reruns; a failed stage can retry transactionally on the same Bronze run. Reference business keys and raw comparison expressions use BIN2 plus byte-length checks, and accepted keys remain their source-issued identifiers rather than recalculated row numbers. Selected geography can retain a valid region when city is invalid. See [validation summary](VALIDATION.md).

**Step 6C implementation clarification (2026-10-01):** `silver.physical_attempt.is_coherent` describes the full supplied extract. A group whose own scans agree retains its source-issued sequence, time and result even if a different attempt after T creates a full-extract collision. Cutoff and certificate calculations apply conflict holds separately within T and W, respectively. `silver.certificate_check.is_certificate_valid` tests the source-issued certificate through W; `is_first_attempt_eligible` additionally requires cutoff handover, no cutoff terminal hold, and an attempt by T. A trustworthy zero-attempt certificate can therefore be valid while its shipment is outside the first-attempt denominator. The analytics stage stores all four Silver outputs and integration flags in one transaction, rejects completed repeat runs, and leaves Gold and the publication pointer untouched. See [validation summary](VALIDATION.md).

## Conventions and boundaries

Proposed database: `ParcelDeliveryWarehouse`; schemas: `ctl` (technical control), `bronze` (raw parsed CSV fields), `silver` (resolved evidence), and `gold` (five business views). The only business inputs are the six contracted CSVs. A `run_id` is a UUID for one complete six-file refresh. T and E are stored on that run, not taken from the clock: T = `2026-06-28T23:59:59Z`, E = `2026-07-07T23:59:59Z` for the current dataset. UTC values use `datetime2(0)`; SQL Server stores no time-zone offset, so the `_utc` suffix and validated `Z` input are essential. Durations retain exact seconds as `bigint` in Silver and are exposed as `decimal(19,6)` hours in Gold; only reports round to two decimals.

In the inventories below, **NN** means `NOT NULL`, **N** means `NULL`, and `—` means no default. Every column without an explicit default has **no default**. `PK`, `FK`, and `UQ` mean primary key, foreign key, and unique constraint. `char`/`varchar` hold validated ASCII IDs and codes; descriptive text is `nvarchar`. Never truncate an oversized raw value to fit a typed column: keep it in Bronze and apply the source-specific Q/AF rule. Named checks enforce enumerations and nonnegative/positive counts; a view has no insert defaults or physical indexes.

## Bronze: exact raw columns and file boundary

Each Bronze table has these **common columns**, in addition to the source-specific columns listed below: `run_id uniqueidentifier NN`, `source_file_id bigint NN`, `source_name varchar(32) COLLATE Latin1_General_100_BIN2 NN`, `source_row_number int NN`, `loaded_at_utc datetime2(0) NN DEFAULT SYSUTCDATETIME()`. PK `(run_id,source_row_number)`; FK `run_id` to `ctl.refresh_run` and composite FK `(source_file_id,run_id,source_name)` to `ctl.source_file(file_id,run_id,source_name)` so a row cannot claim another run's or source's file; table-specific source-name check and row number ≥ 2. Index `(source_file_id,source_row_number)`. The six tables are distinct because their contracted headers are distinct. **Every source-specific column named below is `nvarchar(max) COLLATE Latin1_General_100_BIN2 NOT NULL` with no default**, holding the exact parsed field string before trimming or conversion; CSV empty/quoted-empty is stored as `N''`. The original file path, byte count and SHA-256 live in `ctl.source_file`; retaining the file plus Bronze values permits provenance checks. Hashes are not used as a substitute for field equality.

## Gold views, keys, and roles

Every view restricts its Silver rows to the single `ctl.published_run.active_run_id`. The Gold views are read-only and have **no column defaults or view indexes**. Their types and semantic nullability below must be made explicit with `CAST` in implementation, especially the Unknown rows. Underlying Silver PKs, not view-generated row numbers, enforce one row per current business key. Stable dimension keys are the valid source business IDs widened to `varchar(20)` plus reserved sentinels `UNK_CUSTOMER`, `UNK_SERVICE`, `UNK_DEPOT`; those sentinels cannot match the source ID patterns. Retain source IDs in Silver for traceability. `date_key=0` means Unknown/not applicable. Gold dimensions each include exactly one Unknown member for the active run.

The fact view joins one summary to one shipment and one certificate check, left joins each unique current master, and maps failed/missing master joins to reserved Unknown keys. A syntactically invalid source FK becomes null in Silver but remains verbatim in Bronze and is flagged; a valid unresolved FK remains visible in Silver and maps Unknown in Gold. The view derives the four date keys by UTC date from typed timestamps, using 0 when absent/unusable; every nonzero key must match `gold.dim_date`. It exposes **no stored percent column**: rates are `SUM(numerator_flag)/SUM(denominator_flag)` with zero denominators displayed N/A. Gold view tests must prove all joins preserve the fact count.

The current-state dimensions reflect selected source versions as of E, even when their attributes changed after T. This is deliberate version-one restatement, not SCD2. The fact retains T and E so a consumer can label its snapshot. A successful delivery is both terminal evidence and one physical attempt; no Gold event fact is introduced.

## Key design checks against fixtures

- Core fixture: 14 Gold fact rows, H=12, D=10; 14 accepted event messages collapse to 10 physical attempts; confirmed on time 4/10; transit totals 114 hours over 6 eligible shipments; backlog 2/48 hours; first attempt 4/7; coverage 10/12; return/loss 1/10 each. F02's two messages share one attempt ID, F09 is Unknown but tracked, F11 lacks a usable promise yet remains transit eligible, and F14 has a delivery but no first-attempt eligibility.
- Wider certificate: both F04 variants have two attempts through W and only a failed first attempt by T. C=2 validates and leaves F04 first-attempt eligible as a failure; C=3 fails reconciliation and excludes it. The success after T never becomes a T delivery or second T attempt. The Step 6C SQL fixture and variant checks are recorded in [validation summary](VALIDATION.md); the Gold projection follows those Silver results.
- Source accounting must satisfy `R=AC+AF+DX+DE+DS+Q` per file; reporting splits are separate: accepted shipments = fact + future booking, accepted events = by-T usable + by-T without valid handover + after-T. See the governing event rules for H/D/outcome/first-attempt partitions.

No genuine design blocker is known. Step 5 confirmed the local SQL connection and Python ODBC client; see [validation summary](VALIDATION.md). SQL Server's local certificate is not client-trusted, so the explicit local-only trust exception must be replaced with a trusted certificate for remote or production use.
